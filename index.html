THE OPERATING MODEL

One system.
Many bottlenecks.

Start with the customer workload: model, input and output lengths, and concurrency. The serving engine turns that workload into prefill and decode, using KV cache across a hierarchy of memory and potentially a network.

Every optimisation should connect back to latency, throughput, quality and cost. A win in one metric is not automatically a customer win.

WORKLOAD → SERVING → COMPUTE + MEMORY → PERFORMANCE → COST

01

THE REQUEST LIFECYCLE

Inference Fundamentals

Prefill processes the prompt and creates attention state; decode generates output sequentially while reusing that state. Prefill is often compute-heavy, while decode is frequently limited by memory movement. The actual bottleneck depends on the workload and hardware.

Start with prefill vs decode ↗
02

MEASURE WHAT MATTERS

Performance & Benchmarking

TTFT captures the wait for the first token; TPOT describes generation pace; throughput captures aggregate work. Compare results with the same model, input/output lengths, concurrency, precision, software and latency objectives. A throughput gain that breaks an SLO may not be a useful gain.

Understand the metrics ↗
03

THE WORKING MEMORY

KV Cache & Memory

KV cache avoids recomputing prior attention state, but grows with context and concurrent sequences. Paging reduces allocation waste; prefix reuse avoids repeat prefill; tiering, quantisation and eviction trade capacity against retrieval time, quality and recomputation.

Explore KV cache ↗
04

FROM MODEL TO SERVICE

Serving Engines

Serving engines schedule requests, manage memory and execute model operations. vLLM, SGLang, TensorRT-LLM and llama.cpp have different strengths; none is universally fastest. Compare the complete stack against the actual workload and constraints.

Compare serving engines ↗
05

SEPARATE TO SPECIALISE

Disaggregated Inference

Separate prefill and decode workers can scale independently and specialise for different bottlenecks. The price is coordination and KV transfer. The critical question is whether utilisation gains exceed the transfer and scheduling overhead on the critical path.

See the trade-off ↗
06

MOVING STATE

GPU Networking & Data Movement

Moving KV between workers or memory tiers consumes bandwidth and time. RDMA and GPU-direct paths can reduce host involvement; overlapping transfer with computation can hide some of its cost. Measure exposed communication, not just raw transfer time.

Explore data movement ↗
07

THE EXECUTION LAYER

Kernels & Optimisation

Custom and fused kernels can reduce memory traffic and launch overhead. Roofline analysis relates arithmetic intensity to compute and bandwidth ceilings; speculative decoding uses cheaper proposals to potentially advance generation faster. Each requires workload-specific measurement.

Explore optimisation ↗
08

BITS, SPEED & QUALITY

Precision & Quantisation

Representing weights, activations or KV state with fewer bits can reduce memory pressure and sometimes improve speed. Benefits depend on hardware support and conversion costs. Measure end-to-end performance and quality, and identify which operations actually use the lower precision.

Understand precision ↗
09

SYSTEMS, NOT SPECS

Hardware & System Architecture

GPU compute is only one part of the path. HBM, host DRAM, storage, the CPU, NICs and fabric all shape performance. Faster kernels can expose memory or network bottlenecks; peak FLOPS alone cannot predict application performance.

Explore the hierarchy ↗

LONG-LIVED WORKLOADS

Agentic AI Systems

Agent workflows loop through model calls and tools, often growing and reusing context across turns or subagents. They put pressure on scheduling, cache persistence and long-context capacity. Shared KV can help only when useful reuse outweighs retrieval and coordination costs.

Card 1. Prefill vs Decode ⭐⭐⭐

In one sentence

An LLM request has two very different phases: prefill processes the input prompt, while decode generates the output tokens one at a time.

Mental model

PROMPT → PREFILL → KV CACHE → DECODE → TOKENS

What's actually happening?

Prefill

  • Processes many input tokens in parallel.
  • Builds the Key-Value (KV) cache.
  • Often makes heavy use of GPU compute.

Decode

  • Generates tokens sequentially.
  • Constantly reads previously generated KV state.
  • Frequently becomes dominated by memory movement/bandwidth rather than pure compute.

Why should I care?

Because an optimisation can improve one phase and do almost nothing for the other.

That is why you should be suspicious of:

"Performance improved 25%."

Your question becomes:

"Which phase improved, prefill or decode, and at what Input Sequence Length, Output Sequence Length and concurrency?"

Metrics to connect

  • Time to First Token (TTFT) → strongly influenced by prefill.
  • Time per Output Token (TPOT) → decode responsiveness.
  • Output throughput → rate of output-token generation.
  • Tokens/second/GPU → infrastructure efficiency.

Remember

Prefill = understand the prompt. Decode = produce the answer.

Card 2. Compute-bound vs Memory-bound ⭐⭐⭐

One sentence

A workload is compute-bound when arithmetic capacity limits performance and memory-bound when supplying data to the compute units limits performance.

Mental picture

A GPU has:

Huge compute engine ← data must arrive fast enough ← HBM

If the compute units are waiting for data, adding more theoretical FLOPS doesn't necessarily solve the problem.

Why it matters for your work

This explains why comparing GPUs using only peak FLOPS can be misleading.

A decode workload may care enormously about:

  • High Bandwidth Memory (HBM) bandwidth
  • memory capacity
  • cache efficiency
  • kernel efficiency

Engineering question

"Are we compute-bound or memory-bandwidth-bound at this concurrency, and what evidence from profiling supports that?"

Remember

More FLOPS don't help if the GPU is waiting for data.

Card 3. TTFT vs TPOT vs Throughput ⭐⭐⭐

These should become almost automatic for you.

MetricPlain EnglishCustomer perception
TTFTTime waiting before first token"How quickly did it respond?"
TPOTTime between generated tokens"How fast is it responding?"
ThroughputTotal work completed per time"How much traffic can it serve?"

Important TPM lesson

You cannot call something a performance win from throughput alone.

Example:

Throughput +20%, TTFT +45%

could mean the system serves more total traffic but individual users wait considerably longer.

Engineering question

"What throughput did we achieve while maintaining the customer's latency Service-Level Objective?"

Remember

Latency tells me the experience. Throughput tells me the capacity.

Card 4. What is the KV Cache? ⭐⭐⭐

One sentence

The Key-Value cache stores intermediate attention state from tokens already processed so the model doesn't repeatedly recompute them while generating each new token.

Without caching:

1     Token 1 → compute previous context
2     Token 2 → compute previous context again
3     Token 3 → compute it again
4     ...

With KV cache:

1     Previous computation → stored
2                            ↓
3     New token → reuse previous KV → compute only what's new

Why this is becoming critical

As:

  • context grows,
  • concurrency grows,
  • models support longer conversations,
  • coding/agent sessions become persistent,

KV memory becomes enormous.

Eventually the problem is no longer simply:

"Will the model weights fit?"

but:

"Will the model + KV state for all concurrent users fit?"

Remember

Weights are the model's knowledge. KV cache is the conversation's working memory.

Card 5. PagedAttention ⭐⭐⭐

Problem

KV memory can become fragmented as many requests of different lengths arrive and leave.

Mechanism

PagedAttention breaks KV cache into smaller fixed-size blocks/pages rather than requiring large contiguous areas of GPU memory.

Conceptually this resembles virtual memory.

1     Logical request
2     1 2 3 4 5
3
4           ↓ mapping
5
6     KV blocks in different
7     physical memory locations

Benefit

Better memory utilisation and support for more concurrent sequences.

This is one of the important concepts associated with vLLM.

Engineering question

"Is our limitation actual KV capacity or inefficient KV allocation/fragmentation?"

Remember

PagedAttention manages KV memory in blocks rather than demanding one contiguous allocation.

Card 6. Prefix Caching ⭐⭐⭐

Problem

Users frequently send prompts containing identical content.

Examples:

  • system prompts
  • common documents
  • shared coding repositories
  • repeated agent instructions
  • multi-turn conversation history

Why recompute the same prefix repeatedly?

Mechanism

Store the KV cache produced for the shared prefix and reuse it.

1     Repeated prefix
2           ↓
3     Cached KV exists?
4        ↓ YES
5     Reuse KV
6        ↓
7     Skip prefill computation

Benefit

Potential improvements to:

  • TTFT
  • GPU utilisation
  • throughput
  • cost/token

Critical variable

Cache hit rate.

A wonderful caching architecture with almost no reusable prefixes may provide little benefit.

Engineering question

"What's our prefix-cache hit rate on representative production traffic?"

Card 7. KV Cache Hit Rate ⭐⭐⭐

This is one I particularly want you to remember.

Definition

Percentage of requested KV state found in cache rather than requiring recomputation.

1     100 requests for reusable KV
2
3     86 found
4     14 missing
5
6     Hit rate = 86%

Why it matters

Higher useful hit rate can mean:

fewer prefill computations → less GPU work → lower latency → higher effective throughput

One workload-specific result reports a move from 75.2% → 86.8% cache hit rate, alongside claims of approximately 2× goodput and lower p95 TTFT.

Do not memorise those performance numbers as universal.

Memorise the relationship.

Engineering question

"Did performance improve because KV transfers became faster, because hit rate increased, or because KV became smaller?"

Card 8. Hierarchical KV Cache / LMCache ⭐⭐⭐

Problem

GPU High Bandwidth Memory is extremely valuable and limited.

Keeping every KV block there doesn't scale.

Solution

Create a memory hierarchy:

1     FAST / EXPENSIVE
2            HBM
3             ↓
4         CPU DRAM
5             ↓
6           NVMe
7     SLOWER / LARGER

Systems such as LMCache manage KV state beyond GPU HBM so useful state can be retained and restored later.

Critical trade-off

Retrieving cached KV must be cheaper than recomputing it.

Therefore:

cache hit alone isn't sufficient

You care about:

hit rate + retrieval latency + bandwidth + recomputation cost

Engineering question

"For each storage tier, what's the break-even point between retrieving KV and recomputing prefill?"

Card 9. KV Quantisation ⭐⭐⭐

Problem

KV cache consumes enormous amounts of memory.

Mechanism

Represent KV values using fewer bits.

Conceptually:

1     BF16 KV
2        ↓
3     FP8 / INT8 / INT4-style representation
4        ↓
5     smaller KV

Benefit

Smaller KV can mean:

  • more concurrent users
  • longer context
  • higher cache residency
  • less data transferred
  • potentially higher hit rates

But…

Quantisation may introduce:

  • accuracy impacts
  • conversion overhead
  • kernel complexity
  • compatibility issues

One supplied post describes combining a 4-bit TurboQuant KV cache with LMCache, with sensitive layers remaining in BF16.

Engineering question

"What memory reduction do we get, and what quality or conversion overhead do we pay?"

Remember

KV quantisation makes conversation memory smaller, not necessarily computation faster.

Card 10. Cache Eviction

Problem

Eventually the cache is full.

Something has to leave.

Mechanism

An eviction policy chooses what to discard.

Conceptually:

1     HOT KV → keep
2
3     WARM KV → maybe move
4
5     COLD KV → DRAM/NVMe or evict

The TPM insight

An eviction decision affects future latency.

Evict something that gets reused soon:

→ cache miss → re-prefill

→ GPU compute → latency increase.

Engineering question

"What does the eviction policy optimise for: recency, frequency, size, retrieval cost or expected reuse?"

Card 11. Prefill-Decode Disaggregation ⭐⭐⭐

Problem

Prefill and decode have different hardware characteristics.

So why force both onto exactly the same resources?

Mechanism

1     Request
2        ↓
3     PREFILL GPUs
4        ↓
5     KV cache transfer
6        ↓
7     DECODE GPUs
8        ↓
9     Generated tokens

You can then scale the two independently.

Potential benefit

Higher utilisation through workload specialisation.

New problem

The KV cache now has to move.

If KV movement takes too long:

the network can erase the benefit of disaggregation.

Engineering question

This is the one I want you to retain:

"Where is the break-even point where improved GPU utilisation exceeds KV-transfer and scheduling overhead?"

That's a very good TPM Director question.

Card 12. Incremental KV Transfer

Naive implementation

1     Finish entire prefill
2            ↓
3     Transfer entire KV
4            ↓
5     Start decode

Decode waits for everything.

Better implementation

1     Compute layer 1 KV → transfer
2     Compute layer 2 KV → transfer
3     Compute layer 3 KV → transfer
4     ...
5                         ↓
6             transfer overlaps compute

Data movement occurs while later computation continues.

Principle

Hide communication underneath computation.

This is an extremely useful performance concept beyond KV cache.

Engineering question

"Are we measuring raw KV-transfer time, or the transfer time actually exposed after communication/computation overlap?"

Remember

Performance isn't just how expensive something is. It's how much of the expense sits on the critical path.

Card 13. RDMA / GPU-direct data movement ⭐⭐⭐

RDMA

Remote Direct Memory Access

The basic goal is to move data between machines without forcing the CPU to copy and orchestrate every byte.

Conceptually:

1     Slower / CPU-centric
2
3     GPU → CPU memory → CPU → NIC
4                          ↓
5                        Network
6
7
8     Direct path
9
10     GPU memory → NIC → Network → NIC → GPU memory

GPU-controlled/proxy-free approaches can reduce or remove CPU involvement.

Why you care

At very large scale, unnecessary memory copies can become a serious latency and CPU-overhead problem.

Metrics

  • GB/s
  • line-rate utilisation
  • transfer latency
  • CPU utilisation
  • exposed communication time

Engineering question

"Is KV movement GPU-to-GPU directly, or are we staging through host memory?"

Card 14. Heterogeneous Prefill/Decode

Heterogeneous prefill/decode is a more advanced version of PD disaggregation.

Instead of:

AMD GPU → AMD GPU

you might conceptually have:

Accelerator A → Accelerator B

with each specialised for a different phase.

Problem

Different accelerator architectures may have:

  • different KV layouts
  • numerical formats
  • memory organisation
  • networking capabilities

Therefore transferring KV becomes considerably more complicated.

The TPM question

"Is the KV representation interoperable between the two accelerators, or do we need conversion/reformatting on the transfer path?"

Remember

Disaggregation gets harder when compute becomes heterogeneous.

Card 15. vLLM vs SGLang vs TensorRT-LLM vs llama.cpp

Don't memorise the simplistic "which one is fastest?" graphics.

Use this mental model:

vLLM

Think:

general-purpose high-throughput model serving + PagedAttention + continuous batching

SGLang

Think:

high-performance serving with strong scheduling, structured/agentic workload capabilities and RadixAttention-style prefix reuse

TensorRT-LLM

Think:

NVIDIA-focused heavily optimised inference stack

llama.cpp

Think:

lightweight/portable inference, particularly CPU and edge/local scenarios

TPM lesson

There is no meaningful statement:

"Framework X is fastest."

without:

model + accelerator + precision + sequence length + concurrency + latency target + software version

Engineering question

"Why was this engine chosen for this exact model and customer workload?"

Card 16. Structured / Grammar-Constrained Generation

Problem

Applications often need guaranteed structured output:

1     {
2       "customer": "...",
3       "priority": "...",
4       "status": "..."
5     }

Telling a model:

"Please output valid JSON"

doesn't guarantee valid JSON.

Mechanism

Grammar-constrained decoding restricts which next tokens are legally selectable.

Benefit

More reliable:

  • JSON
  • schema
  • tool calls
  • agent interfaces

Trade-off

Constraint processing itself can affect serving performance.

Engineering question

"Is structured output enforced during decoding or validated/retried afterwards?"

Card 17. Triton and Custom Kernels

One sentence

A kernel is specialised GPU code implementing operations such as attention, matrix operations or normalisation.

Framework operation:

1     PyTorch
2        ↓
3     generic operations

Optimised path:

1     Fused/custom kernel
2            ↓
3     less memory traffic
4     fewer launches
5     better hardware utilisation

Triton provides a higher-level way of writing GPU kernels than working entirely at the lowest GPU programming level.

Important concept: fusion

Instead of:

1     Read memory → operation A
2     write memory
3     read memory → operation B
4     write memory

combine operations:

1     read → A + B → write

Memory movement decreases.

Engineering question

"Is the uplift coming from higher compute utilisation, reduced memory traffic or fewer kernel launches?"

Card 18. Roofline Analysis ⭐⭐

Purpose

Roofline analysis asks:

What fundamentally limits this operation: compute capability or memory bandwidth?

It relates:

arithmetic intensity = computation performed / bytes moved

Low arithmetic intensity:

→ likely memory-bound.

High arithmetic intensity:

→ potentially compute-bound.

Why this matters

It prevents blindly optimising compute when the workload is actually waiting for memory.

Remember

Roofline tells me which ceiling I'm hitting.

Card 19. Speculative Decoding ⭐⭐⭐

Particularly relevant to the performance updates you regularly review.

Problem

Large-model decoding is expensive because tokens are produced sequentially.

Idea

Have a cheaper mechanism propose several likely tokens.

The large model then verifies them.

1     DRAFT:
2     A B C D
3
4     TARGET MODEL:
5     ✓ ✓ ✓ X
6
7     Accept A B C
8     reject D
9     continue

If several proposed tokens are accepted, the system advances multiple tokens for less target-model work.

Metrics that matter

  • draft depth
  • acceptance rate
  • TPOT
  • output throughput
  • additional overhead
  • quality equivalence

Critical TPM point

Saying:

"Speculative decoding enabled"

doesn't establish value.

Ask:

"What acceptance rate are we achieving and what's the resulting end-to-end throughput/TPOT uplift?"

Card 20. Tokens per GPU vs Cost per Token ⭐⭐⭐

Marketing claims should be independently validated.

Infrastructure view

tokens/sec/GPU

asks:

How productive is each GPU?

Economic view

cost/token

asks:

How much infrastructure cost is required to generate the useful output?

Simplified:

But real Total Cost of Ownership (TCO) can additionally include:

  • power
  • cooling
  • networking
  • CPU
  • storage
  • utilisation
  • software
  • operations

TPM lesson

A GPU that costs more per hour can still have lower cost/token if it produces proportionally more usable tokens while meeting the same Service-Level Objective.

Engineering/business question

"What's cost per million tokens at the customer's required latency target, rather than peak unconstrained throughput?"

Card 21. Precision: BF16, FP8, FP4 ⭐⭐⭐

Mental model

Lower precision means fewer bits representing numbers.

Roughly:

1     BF16
2      ↓
3     FP8
4      ↓
5     FP4
6
7     smaller / potentially faster

Possible benefits:

  • lower memory consumption
  • lower memory bandwidth requirements
  • higher computational throughput

Possible costs:

  • accuracy degradation
  • quantisation complexity
  • unsupported operations
  • fallback paths
  • conversion overhead

Never accept

"FP4 is faster."

Ask:

"Which parts of the model are actually FP4, which remain BF16/FP8, and what accuracy and end-to-end performance were measured?"

That distinction matters directly to many of the benchmark discussions you encounter.

Traditional chatbot:

Agentic workload:

1     prompt
2      ↓
3     reason
4      ↓
5     tool
6      ↓

8      ↓

12      ↓

Context therefore continues growing.

Multiple subagents may also appear.

Consequences

Agentic workloads put increasing pressure on:

  • KV capacity
  • prefix reuse

  • long-context performance

Remember

Agentic inference turns KV cache from an implementation detail into infrastructure.

Card 23. Shared / Global KV Pools ⭐⭐⭐

Traditional model

Each server owns the KV cache created locally.

1     Server A    Server B
2     KV A        KV B

Problem: Server B may need something Server A already computed.

Shared approach

1             Shared KV pool
2            ↗      ↑      ↖
3        Server A Server B Server C

Related ideas and projects include LMCache, ATOM/ATOMesh, Mooncake and AMD Infinity Context.

Expected opportunity

Greater shareability may increase useful KV-cache hit rates and avoid repeated prefill work.

But

Remote reuse only helps when:

retrieval cost < recomputation cost

and transfer latency remains bounded.

TPM question

"What's the marginal benefit in useful hit rate versus the additional network and storage latency?"

Card 25. MI300/MI350/MI355X-class System Thinking

When engineering gives you a hardware result, don't think only:

GPU.

Think:

1     MODEL
2      ↓
3     SERVING ENGINE
4      ↓
5     KERNELS
6      ↓
7     GPU compute
8      ↕
9     HBM
10      ↕
11     CPU / DRAM
12      ↕

THE CONVERSATION STARTERS

Engineering
questions.

Use these to turn an optimisation claim into an evidence-based discussion.

  1. What bottleneck are we removing, and what profiling evidence identifies it?
  2. Which metric improved, under what model, sequence lengths, concurrency and latency SLO?
  3. What changed for TTFT, TPOT, throughput and quality—not just the headline number?
  4. Is KV reuse or retrieval cheaper than recomputing the same prefix?
  5. How much communication remains on the critical path after overlap?
  6. What is the cost per useful token at the customer’s latency target?
  7. What trade-off or new bottleneck did the change introduce?

QUICK REFERENCE

Glossary.

The vocabulary behind the system.

Prefill
Processing the input prompt and producing initial attention state before generation.
Decode
Generating output tokens sequentially while using prior context.
KV cache
Stored attention keys and values for processed tokens, reused during inference.
TTFT
Time to first token: elapsed time before the first output token arrives.
TPOT
Time per output token: a measure of generation pace after the first token.
Throughput
Work completed per unit time, such as output tokens per second.
Goodput
Useful work completed per unit time while meeting the chosen service objectives; definitions vary.
SLO
Service-level objective: a measurable target for service performance.
ISL / OSL
Input sequence length / output sequence length, typically measured in tokens.
HBM
High-bandwidth memory close to the accelerator, used for active model and inference state.
DRAM / NVMe
Host memory / a storage interface, often used as larger but slower tiers than GPU memory.
RDMA
Remote direct memory access: a way to transfer data across machines with reduced CPU involvement.
Arithmetic intensity
Operations performed per byte moved, used to reason about compute and bandwidth limits.
Quantisation
Representing values with reduced precision to reduce storage or enable faster computation.
Prefix cache hit
Finding reusable state for a matching prefix; specify whether the hit rate counts requests, tokens or blocks.
Critical path
The sequence of dependent work that determines completion time; only exposed delays extend it.
