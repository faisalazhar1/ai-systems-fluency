THE OPERATING MODEL

One system.
Many bottlenecks.

Start with the customer workload: model, input and output lengths, and concurrency. The serving engine turns that workload into prefill and decode, using KV cache across a hierarchy of memory and potentially a network.

Every optimisation should connect back to latency, throughput, quality and cost. A win in one metric is not automatically a customer win.

WORKLOAD → SERVING → COMPUTE + MEMORY → PERFORMANCE → COST

01

THE REQUEST LIFECYCLE

Inference Fundamentals

Prefill processes the prompt and creates attention state; decode generates output sequentially while reusing that state. Prefill is often compute-heavy, while decode is frequently limited by memory movement. The actual bottleneck depends on the workload and hardware.

02

MEASURE WHAT MATTERS

Performance & Benchmarking

TTFT captures the wait for the first token; TPOT describes generation pace; throughput captures aggregate work. Compare results with the same model, input/output lengths, concurrency, precision, software and latency objectives. A throughput gain that breaks an SLO may not be a useful gain.

Understand the metrics ↗
03

THE WORKING MEMORY

KV Cache & Memory

KV cache avoids recomputing prior attention state, but grows with context and concurrent sequences. Paging reduces allocation waste; prefix reuse avoids repeat prefill; tiering, quantisation and eviction trade capacity against retrieval time, quality and recomputation.

Explore KV cache ↗
04

FROM MODEL TO SERVICE

Serving Engines

Serving engines schedule requests, manage memory and execute model operations. vLLM, SGLang, TensorRT-LLM and llama.cpp have different strengths; none is universally fastest. Compare the complete stack against the actual workload and constraints.

Compare serving engines ↗
05

SEPARATE TO SPECIALISE

Disaggregated Inference

Separate prefill and decode workers can scale independently and specialise for different bottlenecks. The price is coordination and KV transfer. The critical question is whether utilisation gains exceed the transfer and scheduling overhead on the critical path.

See the trade-off ↗
06

MOVING STATE

GPU Networking & Data Movement

Moving KV between workers or memory tiers consumes bandwidth and time. RDMA and GPU-direct paths can reduce host involvement; overlapping transfer with computation can hide some of its cost. Measure exposed communication, not just raw transfer time.

Explore data movement ↗
07

THE EXECUTION LAYER

Kernels & Optimisation

Custom and fused kernels can reduce memory traffic and launch overhead. Roofline analysis relates arithmetic intensity to compute and bandwidth ceilings; speculative decoding uses cheaper proposals to potentially advance generation faster. Each requires workload-specific measurement.

Explore optimisation ↗
08

BITS, SPEED & QUALITY

Precision & Quantisation

Representing weights, activations or KV state with fewer bits can reduce memory pressure and sometimes improve speed. Benefits depend on hardware support and conversion costs. Measure end-to-end performance and quality, and identify which operations actually use the lower precision.

Understand precision ↗
09

SYSTEMS, NOT SPECS

Hardware & System Architecture

GPU compute is only one part of the path. HBM, host DRAM, storage, the CPU, NICs and fabric all shape performance. Faster kernels can expose memory or network bottlenecks; peak FLOPS alone cannot predict application performance.

Explore the hierarchy ↗
10

LONG-LIVED WORKLOADS

Agentic AI Systems

Agent workflows loop through model calls and tools, often growing and reusing context across turns or subagents. They put pressure on scheduling, cache persistence and long-context capacity. Shared KV can help only when useful reuse outweighs retrieval and coordination costs.

Explore agentic workloads ↗
11

AI IN THE DEVELOPMENT LOOP

AI Software Engineering

Persistent agent context can reduce repeated discovery across sessions, while automated review can assist human reviewers. Judge the system by completed work, defects, review burden and recovery, not just generated lines or pull request count.

THE REFERENCE DECK / 27 CARDS

Technical cards.

Build fluency with a repeatable chain: problem → mechanism → metric → trade-off → question.

01 / INFERENCE

Prefill vs Decode

Problem. Prompt processing and token generation have different performance profiles.

Mechanism. Prefill processes input and builds KV state; decode generates tokens sequentially using that state.

Measure & trade-off. TTFT, TPOT and throughput; improving one phase may not help the other.

Which phase improved, at what input/output lengths and concurrency?

02 / INFERENCE

Compute-bound vs Memory-bound

Problem. Peak compute does not guarantee application speed.

Mechanism. An operation may be limited by arithmetic capacity or by the rate at which data reaches compute units.

Measure & trade-off. Profile utilisation and bandwidth at representative concurrency; bottlenecks can change with workload.

Which resource is limiting us, and what profiling evidence supports that?

03 / PERFORMANCE

TTFT, TPOT & Throughput

Problem. Capacity and user experience are not the same thing.

Mechanism. TTFT is the wait for the first token; TPOT describes per-output-token time; throughput is work completed per unit time.

Measure & trade-off. Report latency distributions alongside output throughput and SLOs; batching may increase throughput while increasing latency.

What throughput did we achieve while meeting the customer’s latency SLO?

04 / KV CACHE

What is the KV Cache?

Problem. Recomputing attention state for prior tokens wastes work during generation.

Mechanism. Cache keys and values for processed tokens and reuse them as new tokens are generated.

Measure & trade-off. Track KV memory and concurrency; avoiding recomputation consumes memory that grows with context.

Will weights and KV state fit for the expected context lengths and concurrency?

05 / KV CACHE

PagedAttention

Problem. Variable-length requests can waste or fragment KV memory.

Mechanism. Manage KV state in fixed-size blocks mapped to logical sequences rather than requiring contiguous allocation.

Measure & trade-off. Measure allocation efficiency and supported concurrency; block management has overhead and can leave partially filled blocks.

Are we limited by KV capacity or by allocation waste?

06 / KV CACHE

Prefix Caching

Problem. Requests may repeatedly process the same system prompt or conversation prefix.

Mechanism. Reuse cached KV state for a matching prefix instead of recomputing it.

Measure & trade-off. Measure useful hit rate, TTFT and cache occupancy; benefits depend on actual prefix reuse.

What is the prefix-cache hit rate on representative production traffic?

07 / KV CACHE

KV Cache Hit Rate

Problem. A cache is only useful if it avoids enough work.

Mechanism. A hit finds requested reusable KV state rather than recomputing it. Define whether the rate counts requests, tokens or blocks.

Measure & trade-off. Compare hit rate with saved prefill, retrieval latency and goodput; a hit can still be too slow to help.

Did the gain come from more useful hits, faster retrieval or smaller KV?

08 / KV CACHE

Hierarchical KV Cache

Problem. GPU HBM is fast but limited.

Mechanism. Systems such as LMCache can retain KV across GPU memory, host DRAM and storage, retrieving it when needed.

Measure & trade-off. Compare tier hit rate and restore latency against prefill recomputation; larger tiers are generally slower.

For each tier, when is retrieval cheaper than recomputation?

09 / QUANTISATION

KV Quantisation

Problem. KV state limits context length and concurrency.

Mechanism. Store KV values at lower precision, sometimes retaining sensitive components at higher precision.

Measure & trade-off. Measure memory reduction, quality and end-to-end latency; conversion and kernel overhead can offset gains.

How much memory do we save, and what quality or conversion cost do we pay?

10 / KV CACHE

Cache Eviction

Problem. A finite cache eventually fills up.

Mechanism. An eviction policy selects state to discard or move to a lower tier.

Measure & trade-off. Track future misses, restore time and recomputation; retaining one item displaces another.

Does the policy optimise recency, frequency, size, retrieval cost or expected reuse?

11 / DISAGGREGATION

Prefill–Decode Disaggregation

Problem. Prefill and decode can have different resource needs.

Mechanism. Run them on separate worker pools and transfer KV between them, enabling independent scaling.

Measure & trade-off. Compare utilisation and SLO goodput against transfer and scheduling overhead; separation adds complexity.

Where is the break-even point between utilisation gains and KV-transfer overhead?

12 / DATA MOVEMENT

Incremental KV Transfer

Problem. Waiting until prefill finishes to transfer all KV can delay decode.

Mechanism. Transfer available KV incrementally while later computation continues, where the implementation permits.

Measure & trade-off. Measure transfer time exposed on the critical path, not only raw transfer duration; coordination can add overhead.

How much transfer time remains exposed after overlap with computation?

13 / NETWORKING

RDMA & GPU-direct Movement

Problem. Host staging and CPU-managed copies can add overhead when moving data between machines.

Mechanism. RDMA and supported GPU-direct paths can reduce CPU involvement and avoid some host-memory copies.

Measure & trade-off. Measure bandwidth, transfer latency, CPU usage and exposed communication; support and topology matter.

Is KV moving directly between GPUs, or being staged through host memory?

14 / DISAGGREGATION

Heterogeneous Prefill & Decode

Problem. Different accelerators may suit different inference phases.

Mechanism. Use different hardware for prefill and decode, transferring state between them.

Measure & trade-off. Measure end-to-end latency and utilisation including layout and numerical conversion; interoperability adds complexity.

Is the KV representation compatible, or must it be converted on the transfer path?

15 / SERVING

Serving Engine Choices

Problem. “Which engine is fastest?” has no workload-independent answer.

Mechanism. vLLM emphasises high-throughput serving and PagedAttention; SGLang includes prefix reuse; TensorRT-LLM targets NVIDIA optimisation; llama.cpp prioritises portable local inference.

Measure & trade-off. Compare model, hardware, precision, sequence lengths, concurrency, SLO and versions; portability and features matter too.

Why was this engine chosen for this model and customer workload?

16 / SERVING

Grammar-Constrained Generation

Problem. Prompting alone does not ensure valid structured output.

Mechanism. Constrained decoding restricts token choices according to a grammar or schema; validation and retry is an alternative.

Measure & trade-off. Measure valid outputs, latency and retry rates; constraints can add decoding overhead and do not guarantee semantic correctness.

Are constraints enforced during decoding or validated and retried afterwards?

17 / KERNELS

Triton & Custom Kernels

Problem. Generic operations may incur unnecessary memory traffic or launches.

Mechanism. Custom GPU kernels, including those written with Triton, can fuse operations and reduce intermediate reads and writes.

Measure & trade-off. Profile bandwidth, utilisation and end-to-end performance; custom code adds maintenance and portability costs.

Is the uplift from compute utilisation, less memory traffic or fewer launches?

18 / KERNELS

Roofline Analysis

Problem. Optimising compute will not help much if data movement is the limiting factor.

Mechanism. Relate arithmetic intensity (operations per byte moved) to compute and bandwidth ceilings.

Measure & trade-off. Compare observed performance with the relevant ceilings; a simplified model must be checked against profiling and the real execution path.

Which ceiling are we hitting for this operation at this workload?

19 / OPTIMISATION

Speculative Decoding

Problem. Sequential decoding can be expensive.

Mechanism. A cheaper proposer drafts tokens and the target model verifies them, potentially advancing multiple tokens per verification step.

Measure & trade-off. Track acceptance rate, draft depth, TPOT, throughput and quality; drafting and verification add overhead.

What acceptance rate and end-to-end uplift do we actually achieve?

20 / ECONOMICS

Tokens per GPU vs Cost per Token

Problem. Peak GPU productivity is not the same as customer economics.

Mechanism. Tokens per second per GPU measures productivity; cost per token connects output to infrastructure and operating expense.

Measure & trade-off. Compare cost per million useful tokens at the same latency SLO, including utilisation and relevant total costs.

What is the cost per million tokens at the customer’s latency target?

21 / PRECISION

BF16, FP8 & FP4

Problem. High-precision representations consume memory and bandwidth.

Mechanism. Lower-precision formats can reduce storage and potentially improve arithmetic throughput on supported hardware.

Measure & trade-off. Measure quality and end-to-end performance; mixed precision, fallback paths and conversion overhead affect results.

Which operations actually use the lower precision, and what quality and speed were measured?

22 / AGENTS

Why Agents Change Inference

Problem. Multi-step agents produce growing, repeated context across model calls and tools.

Mechanism. Long-lived sessions and subagents place pressure on KV capacity, prefix reuse, persistence and scheduling.

Measure & trade-off. Track task latency, cache reuse, context length and cost; retaining state uses scarce capacity.

How does our serving design handle the actual agent loop and context growth?

23 / AGENTS

Shared KV Pools

Problem. One server may need a prefix already computed elsewhere.

Mechanism. A shared or distributed KV pool makes reusable state available across workers.

Measure & trade-off. Compare useful hit-rate gains with network and storage latency; remote retrieval must beat recomputation to help.

What is the marginal benefit of sharing after transfer and coordination costs?

24 / HARDWARE

HBM, DRAM & NVMe

Problem. Fast memory is limited and expensive.

Mechanism. Place active state in GPU HBM, and potentially warmer or colder state in host DRAM or NVMe storage.

Measure & trade-off. Measure restore latency and capacity by tier; larger tiers are generally slower and require movement.

When is restoring KV from each tier cheaper than recomputing it?

25 / HARDWARE

Whole-System Thinking

Problem. Hardware performance cannot be explained by a GPU specification alone.

Mechanism. Model, engine, kernels, GPU, HBM, CPU, network and storage interact; removing one bottleneck can reveal another.

Measure & trade-off. Profile the full stack under a representative workload; local improvements may move the bottleneck elsewhere.

What became the limiting resource after the last optimisation?

26 / SOFTWARE ENGINEERING

Agent Memory & Session Context

Problem. A coding agent may lose architectural decisions and prior progress between sessions.

Mechanism. Persist relevant conventions, decisions, open threads and context in appropriate project files or session records.

Measure & trade-off. Track task completion and human intervention; stale, excessive or sensitive context can create risk.

Which context is durable, current and safe to carry into the next session?

27 / SOFTWARE ENGINEERING

AI-Assisted Code Review

Problem. More generated changes can increase review load and operational risk.

Mechanism. Combine tests, lint, automated review and security checks with risk-based human review and deployment guardrails.

Measure & trade-off. Track completion, defects, review burden and rollback rate; automation can miss important failures.

Which risk classes require human approval, and what happened to defects and rollbacks?

THE CONVERSATION STARTERS

Engineering
questions.

Use these to turn an optimisation claim into an evidence-based discussion.

  1. What bottleneck are we removing, and what profiling evidence identifies it?
  2. Which metric improved, under what model, sequence lengths, concurrency and latency SLO?
  3. What changed for TTFT, TPOT, throughput and quality—not just the headline number?
  4. Is KV reuse or retrieval cheaper than recomputing the same prefix?
  5. How much communication remains on the critical path after overlap?
  6. What is the cost per useful token at the customer’s latency target?
  7. What trade-off or new bottleneck did the change introduce?

QUICK REFERENCE

Glossary.

The vocabulary behind the system.

Prefill
Processing the input prompt and producing initial attention state before generation.
Decode
Generating output tokens sequentially while using prior context.
KV cache
Stored attention keys and values for processed tokens, reused during inference.
TTFT
Time to first token: elapsed time before the first output token arrives.
TPOT
Time per output token: a measure of generation pace after the first token.
Throughput
Work completed per unit time, such as output tokens per second.
Goodput
Useful work completed per unit time while meeting the chosen service objectives; definitions vary.
SLO
Service-level objective: a measurable target for service performance.
ISL / OSL
Input sequence length / output sequence length, typically measured in tokens.
HBM
High-bandwidth memory close to the accelerator, used for active model and inference state.
DRAM / NVMe
Host memory / a storage interface, often used as larger but slower tiers than GPU memory.
RDMA
Remote direct memory access: a way to transfer data across machines with reduced CPU involvement.
Arithmetic intensity
Operations performed per byte moved, used to reason about compute and bandwidth limits.
Quantisation
Representing values with reduced precision to reduce storage or enable faster computation.
Prefix cache hit
Finding reusable state for a matching prefix; specify whether the hit rate counts requests, tokens or blocks.
Critical path
The sequence of dependent work that determines completion time; only exposed delays extend it.
