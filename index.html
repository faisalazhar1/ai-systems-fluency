THE OPERATING MODEL

One system.
Many bottlenecks.

Start with the customer workload: model, input and output lengths, and concurrency. The serving engine turns that workload into prefill and decode, using KV cache across a hierarchy of memory and potentially a network.

Every optimisation should connect back to latency, throughput, quality and cost. A win in one metric is not automatically a customer win.

01

THE REQUEST LIFECYCLE

Inference Fundamentals

Prefill processes the prompt and creates attention state; decode generates output sequentially while reusing that state. Prefill is often compute-heavy, while decode is frequently limited by memory movement. The actual bottleneck depends on the workload and hardware.

MEASURE WHAT MATTERS

Performance & Benchmarking

TTFT captures the wait for the first token; TPOT describes generation pace; throughput captures aggregate work. Compare results with the same model, input/output lengths, concurrency, precision, software and latency objectives. A throughput gain that breaks an SLO may not be a useful gain.

Understand the metrics ↗
03

THE WORKING MEMORY

KV Cache & Memory

KV cache avoids recomputing prior attention state, but grows with context and concurrent sequences. Paging reduces allocation waste; prefix reuse avoids repeat prefill; tiering, quantisation and eviction trade capacity against retrieval time, quality and recomputation.

Explore KV cache ↗
04

FROM MODEL TO SERVICE

Serving Engines

Serving engines schedule requests, manage memory and execute model operations. vLLM, SGLang, TensorRT-LLM and llama.cpp have different strengths; none is universally fastest. Compare the complete stack against the actual workload and constraints.

Compare serving engines ↗
05

SEPARATE TO SPECIALISE

Disaggregated Inference

Separate prefill and decode workers can scale independently and specialise for different bottlenecks. The price is coordination and KV transfer. The critical question is whether utilisation gains exceed the transfer and scheduling overhead on the critical path.

See the trade-off ↗
06

MOVING STATE

GPU Networking & Data Movement

Moving KV between workers or memory tiers consumes bandwidth and time. RDMA and GPU-direct paths can reduce host involvement; overlapping transfer with computation can hide some of its cost. Measure exposed communication, not just raw transfer time.

Explore data movement ↗
07

THE EXECUTION LAYER

Kernels & Optimisation

Custom and fused kernels can reduce memory traffic and launch overhead. Roofline analysis relates arithmetic intensity to compute and bandwidth ceilings; speculative decoding uses cheaper proposals to potentially advance generation faster. Each requires workload-specific measurement.

Explore optimisation ↗
08

BITS, SPEED & QUALITY

Precision & Quantisation

Representing weights, activations or KV state with fewer bits can reduce memory pressure and sometimes improve speed. Benefits depend on hardware support and conversion costs. Measure end-to-end performance and quality, and identify which operations actually use the lower precision.

Understand precision ↗
09

SYSTEMS, NOT SPECS

Hardware & System Architecture

GPU compute is only one part of the path. HBM, host DRAM, storage, the CPU, NICs and fabric all shape performance. Faster kernels can expose memory or network bottlenecks; peak FLOPS alone cannot predict application performance.

Agentic AI Systems

Agent workflows loop through model calls and tools, often growing and reusing context across turns or subagents. They put pressure on scheduling, cache persistence and long-context capacity. Shared KV can help only when useful reuse outweighs retrieval and coordination costs.

01 / INFERENCE FUNDAMENTALS

Prefill vs Decode

One request, two phases—and two very different performance profiles.

PROMPT → PREFILL → KV CACHE → DECODE → TOKENS
Explore the concept

What happens

Prefill processes many input tokens in parallel and builds the KV cache. It often makes heavy use of GPU compute. Decode generates tokens one at a time, repeatedly reading prior KV state; it is often constrained by memory bandwidth.

Why it matters

An optimisation can improve one phase without helping the other. A claim like “performance improved 25%” is incomplete without the phase and workload.

Watch: TTFT for the initial response; TPOT for generation pace; output throughput and tokens/second/GPU for capacity and efficiency. Input length, output length and concurrency change the result.

Remember: prefill processes the prompt; decode produces the answer.

Which phase improved, at what input/output lengths and concurrency?

02 / INFERENCE FUNDAMENTALS

Compute-bound vs Memory-bound

More theoretical FLOPS do not help much if the compute units are waiting for data.

HBM → DATA MOVEMENT → GPU COMPUTE
Explore the concept

Two different ceilings

Compute-bound: available arithmetic capacity limits the operation. Memory-bound: data cannot be supplied to the compute units fast enough.

Why it matters

Peak FLOPS alone is a poor way to compare GPUs for a specific workload. Decode can depend heavily on HBM bandwidth and capacity, cache efficiency and kernel efficiency. The limiting resource can change with concurrency.

Watch: measured compute utilisation and memory-bandwidth utilisation, supported by profiling of the actual workload.

Remember: match the optimisation to the ceiling you are actually hitting.

Are we compute-bound or memory-bandwidth-bound at this concurrency, and what profiling evidence supports that?

03 / PERFORMANCE

TTFT vs TPOT vs Throughput

Latency describes the experience. Throughput describes the capacity.

FIRST RESPONSE → GENERATION PACE → TOTAL CAPACITY
Explore the concept

Three questions, three metrics

  • TTFT: How long until the first token? “How quickly did it respond?”
  • TPOT: How much time per output token? “How fast is it responding?”
  • Throughput: How much work is completed per unit time? “How much traffic can it serve?”

Read the trade-off

For example, throughput +20% and TTFT +45% could mean more total traffic served while individual users wait much longer. Report latency distributions as well as throughput; batching or higher concurrency may change both.

Remember: a throughput win is not automatically a customer win.

What throughput did we achieve while maintaining the customer’s latency SLO?

04 / KV CACHE & MEMORY

What is the KV Cache?

It is the conversation’s working memory: stored attention state for tokens already processed.

PAST TOKENS → STORE KEYS + VALUES → REUSE ON DECODE
Explore the concept

Why cache?

Without reuse, prior attention state would need to be recomputed as new tokens are generated. The KV cache keeps the keys and values from prior tokens so decode can reuse them while computing the new token’s state.

Why it becomes a systems problem

Longer context, more concurrent users and persistent coding or agent sessions all increase KV memory demand. The question is no longer just “Do the weights fit?” but “Do the weights and the KV state for all concurrent requests fit?”

Watch: KV bytes, context length, concurrency, available HBM and memory allocated to weights.

Remember: weights are the model’s knowledge; KV is the conversation’s working memory.

Will model weights and KV state fit for the expected context lengths and concurrency?

05 / KV CACHE & MEMORY

PagedAttention

Manage KV in blocks rather than requiring one large contiguous allocation.

LOGICAL SEQUENCE → BLOCK MAP → PHYSICAL KV BLOCKS
Explore the concept

The problem

Requests arrive and leave with different lengths. Reserving large contiguous memory regions can waste space and cause fragmentation.

The mechanism

PagedAttention divides KV state into fixed-size blocks and maps logical sequence blocks to physical locations, conceptually similar to virtual memory. It is an important concept associated with vLLM.

Benefit: better memory utilisation can support more concurrent sequences. Trade-off: block mapping has overhead and the final block may not be full.

Remember: distinguish actual KV capacity from allocation waste.

Is our limitation actual KV capacity or inefficient allocation and fragmentation?

06 / KV CACHE & MEMORY

Prefix Caching

If a prompt starts with content already processed, reuse its KV state rather than repeat prefill.

MATCHING PREFIX → CACHED KV → SKIP REPEATED PREFILL
Explore the concept

Where reuse comes from

System prompts, shared documents and coding repositories, repeated agent instructions and conversation history can create matching prefixes. A cache stores the KV produced for a prefix so a later matching request can reuse it.

Why it matters

Useful reuse can reduce prefill work and TTFT, and improve effective throughput and cost per token. But the cache occupies memory, and an architecture with little real prefix reuse may deliver little benefit.

Watch: prefix-cache hit rate on representative production traffic, prefill saved, TTFT and cache occupancy.

What is our prefix-cache hit rate on representative production traffic?

07 / KV CACHE & MEMORY

KV Cache Hit Rate

A useful hit avoids work—but only if the saved computation outweighs retrieval.

MORE USEFUL HITS → LESS PREFILL → POTENTIALLY LOWER LATENCY
Explore the concept

Make the denominator explicit

If 86 of 100 comparable requests for reusable KV find it, the request-level hit rate is 86%. Other systems may report hits by token or block; those rates are not interchangeable.

Read reported results carefully

The source describes one workload-specific result moving from 75.2% to 86.8% cache hit rate, alongside claims of approximately 2× goodput and lower p95 TTFT. This is an example, not a universal result or proof of causation.

Watch: useful hits, saved prefill, retrieval latency, KV size and the workload. A hit from a slow tier can still lose to recomputation.

Did performance improve because transfers became faster, hit rate increased, or KV became smaller?

08 / KV CACHE & MEMORY

Hierarchical KV Cache / LMCache

Keep valuable KV beyond limited GPU memory—but make sure it is worth retrieving.

HBM → HOST DRAM → NVMe
faster / smaller → slower / larger
Explore the concept

The mechanism

GPU HBM is fast and scarce. Systems such as LMCache can retain and restore useful KV across a hierarchy that may include host DRAM and storage, rather than keeping every block in HBM.

The break-even

A hit alone is not enough: retrieving state must cost less than recomputing the corresponding prefill, accounting for latency and bandwidth. The answer can differ by tier, prefix length and load.

Watch: hit rate by tier, retrieval latency, available bandwidth and recomputation cost.

For each tier, when is retrieving KV cheaper than recomputing prefill?

09 / PRECISION

KV Quantisation

Use fewer bits for conversation state to reduce memory and data movement.

BF16 KV → LOWER-PRECISION KV → SMALLER FOOTPRINT
Explore the concept

What changes

KV values may be stored in lower-precision formats such as FP8, INT8 or INT4-style representations. Smaller state can support more concurrent users, longer context, greater cache residency and less transfer.

What it costs

Quality may change, and conversion, specialised kernels and compatibility can introduce overhead. The source describes an example combining 4-bit TurboQuant KV with LMCache while keeping sensitive layers in BF16; treat it as an implementation example, not a general performance guarantee.

Watch: memory saved, quality, conversion overhead, transfer size and end-to-end latency.

Remember: smaller conversation memory does not necessarily mean faster computation.

What memory reduction do we get, and what quality or conversion overhead do we pay?

10 / KV CACHE & MEMORY

Cache Eviction

When a cache fills, deciding what leaves determines which future requests pay the price.

HOT → KEEP   /   WARM → TIER   /   COLD → EVICT
Explore the concept

Why the policy matters

Evicting state that is needed again soon leads to a miss, re-prefill, additional GPU work and potentially higher latency. Moving state to a lower tier can preserve it, but a later restore has its own cost.

Decisions and evidence

Policies may consider recency, frequency, size, retrieval cost or expected reuse. These objectives compete: preserving one block means another cannot occupy that capacity.

Watch: future misses, reuse distance, tier restore latency, prefill recomputation and user latency.

What does the eviction policy optimise for: recency, frequency, size, retrieval cost or expected reuse?

11 / DISAGGREGATED INFERENCE

Prefill–Decode Disaggregation

Run prefill and decode on separate workers so each can scale and specialise independently.

REQUEST → PREFILL GPUS → KV TRANSFER → DECODE GPUS
Explore the concept

The opportunity

Prefill and decode have different resource profiles. Separate pools can be sized independently and potentially improve utilisation by specialising each phase.

The new bottleneck

KV must now move between workers. Transfer, scheduling and coordination can erase the utilisation gains if they add too much time or cost on the critical path.

Watch: utilisation, KV-transfer time, scheduling overhead, TTFT, TPOT and goodput under the same SLO as a colocated baseline.

Remember: disaggregation creates a data-movement problem as it solves a resource-allocation problem.

Where is the break-even point where improved utilisation exceeds KV-transfer and scheduling overhead?

12 / DATA MOVEMENT

Incremental KV Transfer

Hide communication under computation instead of waiting for all prefill to finish.

COMPUTE LAYER 1 → TRANSFER   ∥   COMPUTE LAYER 2
Explore the concept

Two approaches

Naive: complete all prefill, transfer all KV, then start decode. Incremental: transfer available layer KV while subsequent layers are still computing, where the serving implementation supports it.

Think in critical-path time

Raw transfer duration can be substantial while the user sees only the portion not hidden by useful computation. Overlap is not free: coordination and resource contention can reduce its benefit.

Watch: raw transfer time, overlap achieved, exposed communication time and end-to-end latency.

Remember: performance depends on how much expense sits on the critical path.

How much transfer time is exposed after communication and computation overlap?

13 / GPU NETWORKING

RDMA & GPU-direct Data Movement

Reduce CPU involvement and avoid unnecessary host-memory staging when moving data between machines.

GPU MEMORY → NIC → NETWORK → NIC → GPU MEMORY
Explore the concept

What the path changes

Remote Direct Memory Access (RDMA) enables data transfer with reduced CPU involvement. Supported GPU-direct paths can let a network interface access GPU memory rather than staging data through host memory. Actual capabilities depend on hardware, drivers and topology.

Why it matters

At scale, extra copies and host orchestration can consume CPU resources and increase transfer latency. Some designs further reduce CPU control using GPU-driven or proxy-free approaches.

Watch: GB/s, line-rate utilisation, transfer latency, CPU utilisation and exposed communication time.

Is KV movement GPU-to-GPU directly, or are we staging through host memory?

14 / DISAGGREGATED INFERENCE

Heterogeneous Prefill & Decode

Different accelerators may suit different phases, but their KV representations must interoperate.

PREFILL ON ACCELERATOR A → CONVERT / TRANSFER → DECODE ON B
Explore the concept

Why it is harder

Accelerators can differ in KV layout, numerical formats, memory organisation and networking capabilities. Specialising each phase may help, but conversion or reformatting can be needed before the receiving worker can use the state.

Watch: transfer and conversion cost, interoperability, phase utilisation and end-to-end latency at the target workload.

Remember: disaggregation gets harder when compute becomes heterogeneous.

Is the KV representation interoperable, or does the transfer path require conversion?

15 / SERVING ENGINES

vLLM, SGLang, TensorRT-LLM & llama.cpp

There is no meaningful universal answer to “Which engine is fastest?”

MODEL + HARDWARE + WORKLOAD + SLO + VERSION
Explore the concept

A useful starting mental model

  • vLLM: general-purpose high-throughput serving, PagedAttention and continuous batching.
  • SGLang: high-performance serving, scheduling and RadixAttention-style prefix reuse, including structured and agentic workloads.
  • TensorRT-LLM: an NVIDIA-focused optimised inference stack.
  • llama.cpp: lightweight, portable local inference, including CPU and edge scenarios.

These are starting points, not permanent rankings. Compare model, accelerator, precision, input/output lengths, concurrency, latency target and software version, as well as deployment and feature requirements.

Why was this engine chosen for this exact model and customer workload?

16 / SERVING ENGINES

Grammar-Constrained Generation

Prompting for JSON does not guarantee a valid structure; decoding constraints can enforce a grammar.

MODEL SCORES → ALLOW LEGAL TOKENS → STRUCTURED OUTPUT
Explore the concept

How it works

Grammar-constrained decoding restricts which next tokens may be selected so output follows a supported grammar or schema. This can make JSON, tool calls and agent interfaces more reliable than an instruction alone.

The trade-off

Constraint processing can affect serving performance. An alternative is to validate after generation and retry on failure; either way, syntactically valid output does not guarantee the content is correct.

Watch: validity, retry rates, latency and semantic quality.

Is structured output enforced during decoding or validated and retried afterwards?

17 / KERNELS & OPTIMISATION

Triton & Custom Kernels

A specialised GPU kernel can reduce memory movement and launch overhead.

READ → OPERATION A + B → WRITE
Explore the concept

What is a kernel?

It is GPU code for an operation such as attention, a matrix operation or normalisation. Triton offers a higher-level way to write GPU kernels than working entirely at the lowest GPU programming level.

Why fusion helps

Separate operations can write an intermediate result and read it back. A fused kernel combines operations, potentially reducing intermediate memory traffic and kernel launches while improving utilisation.

Watch: compute utilisation, memory traffic, kernel launches and end-to-end performance. Custom kernels add complexity and can be hardware-specific.

Is the uplift from compute utilisation, reduced memory traffic or fewer launches?

18 / KERNELS & OPTIMISATION

Roofline Analysis

Relate work per byte to hardware ceilings before deciding what to optimise.

ARITHMETIC INTENSITY = OPERATIONS ÷ BYTES MOVED
Explore the concept

Read the ceiling

At low arithmetic intensity, performance is often constrained by memory bandwidth. At higher intensity it may approach a compute ceiling. The roofline is a model of attainable performance, not a substitute for profiling the real operation.

Why it matters

If an operation is waiting on memory, optimising arithmetic alone may not help. Reducing bytes moved or increasing useful work per byte can be more relevant.

Watch: measured arithmetic intensity, achieved bandwidth and compute rate against the relevant hardware ceilings.

Remember: roofline helps identify which ceiling is being hit.

Which ceiling are we hitting for this operation under this workload?

19 / KERNELS & OPTIMISATION

Speculative Decoding

A cheaper proposer drafts tokens; the target model verifies them to potentially advance faster.

DRAFT A B C D → VERIFY ✓ ✓ ✓ ✗ → ACCEPT A B C
Explore the concept

The mechanism

Decode is sequential. A draft mechanism proposes several likely tokens and the target model verifies them. If enough proposals are accepted, several tokens may be advanced for less target-model work than ordinary sequential generation.

Measure the whole system

Enabling the feature does not establish value. Drafting and verification have costs, and benefits depend on acceptance rate, draft depth and workload. Verify the intended quality or distributional equivalence for the implementation.

Watch: acceptance rate, draft depth, TPOT, output throughput, overhead and output quality.

What acceptance rate and end-to-end throughput or TPOT uplift are we achieving?

20 / PERFORMANCE ECONOMICS

Tokens per GPU vs Cost per Token

Productivity tells you how much a GPU does; economics tells you what useful output costs.

TOKENS / SECOND / GPU → UTILISATION → COST / TOKEN
Explore the concept

Two lenses

Tokens/second/GPU asks how productive each GPU is. Cost/token asks how much infrastructure expense is needed for useful output. A more expensive GPU-hour can still be cheaper per token if it produces proportionally more useful tokens at the same SLO.

Include the real system

Depending on the comparison, total cost may include power, cooling, networking, CPU, storage, utilisation, software and operations. State the cost assumptions and whether input and output tokens are counted separately.

Watch: cost per million useful tokens at the required latency target—not just peak unconstrained throughput.

What is cost per million tokens at the customer’s required latency target?

21 / PRECISION & QUANTISATION

Precision: BF16, FP8 & FP4

Fewer bits can mean smaller or faster computation—but only with suitable support and acceptable quality.

BF16 → FP8 → FP4   /   LESS PRECISION, POTENTIALLY LESS DATA
Explore the concept

Potential benefits and costs

Lower precision can reduce memory capacity and bandwidth needs and potentially increase arithmetic throughput. It can also introduce accuracy loss, quantisation complexity, unsupported operations, fallback paths and conversion overhead.

Look beyond the label

A model advertised as FP4 may still use BF16 or FP8 for some operations. “FP4 is faster” is not enough: establish which components actually use each format, how quality was evaluated and whether the end-to-end workload improved.

Watch: precision by operation, quality, throughput, latency and conversion or fallback overhead.

Which parts use FP4 versus BF16/FP8, and what accuracy and end-to-end performance were measured?

22 / AGENTIC AI

Why Agents Change Inference

Agent sessions repeatedly call models and tools, often with growing and reusable context.

PROMPT → MODEL → TOOL → RESULT → MODEL → …
Explore the concept

From one answer to a workflow

A simple chat exchange may end after one answer. An agent can alternate model calls and tools over many steps, accumulate history and spawn subagents. Context lengths and opportunities for shared prefixes therefore change over time.

What the infrastructure must handle

Pressure grows on KV capacity, prefix reuse, cache persistence, scheduling, memory tiering and long-context performance. Evaluate the complete task, including tool waits and repeated model calls, rather than a single isolated request.

Watch: task latency, context growth, useful cache reuse, capacity and cost.

Remember: agentic inference makes KV cache an infrastructure concern.

How does our serving design handle the real agent loop and context growth?

23 / AGENTIC AI

Shared / Global KV Pools

Share previously computed state across workers instead of restricting reuse to one server.

SERVER A ↔ SHARED KV POOL ↔ SERVER B
Explore the concept

The opportunity

With only local caches, server B may recompute a prefix already processed by server A. A shared pool can make that state available to multiple workers and increase useful reuse. The source references LMCache, ATOM/ATOMesh, Mooncake and AMD Infinity Context as related ideas or projects.

The constraint

Remote reuse is useful only when retrieval costs less than recomputation and transfer latency remains bounded. A larger hit rate alone does not establish an end-to-end win.

Watch: useful hit-rate improvement, retrieval latency, network traffic and avoided prefill.

What is the marginal benefit in useful hit rate versus added network and storage latency?

24 / HARDWARE & ARCHITECTURE

HBM vs DRAM vs NVMe

A memory hierarchy trades speed and cost against capacity.

HBM: HOT → HOST DRAM: WARM → NVMe: COLD
Explore the concept

Three tiers

  • GPU HBM: fastest, relatively small and expensive; suited to active KV.
  • Host DRAM: slower and larger; a possible tier for warm or offloaded KV.
  • NVMe storage: much slower and potentially much larger; a possible tier for persisted or cold KV.

The engineering problem is choosing what belongs where and when to move it. Actual restore time depends on the system, transfer path and load.

Remember: speed ↔ capacity ↔ cost.

What is the observed KV restore latency from each tier, and when is recomputation cheaper?

25 / HARDWARE & ARCHITECTURE

Whole-System Thinking

Performance is a system result, not a single GPU specification.

MODEL → ENGINE → KERNELS → GPU ↔ HBM ↔ CPU / FABRIC
Explore the concept

Follow the bottleneck

Whether evaluating MI300/MI350/MI355X-class systems or another platform, include the model, serving engine, kernels, GPU compute, HBM, CPU/DRAM, NIC/fabric and remote GPUs or storage.

For example, faster kernels may expose a memory-bandwidth limit; a better cache may then expose the network. The “best” next optimisation changes as the bottleneck moves.

Watch: phase-level profiles and end-to-end latency, throughput and cost before and after each change.

Remember: fixing one bottleneck often reveals the next one.

What became the limiting resource after the last optimisation?

26 / AI SOFTWARE ENGINEERING

Agent Memory & Session Context

Persistent context can prevent coding agents from repeatedly reconstructing what a team already knows.

SESSION → DECISIONS + CONVENTIONS → NEXT SESSION
Explore the concept

What to retain

An agent starting a new session may lack the architecture, decisions, previous work, failures and open issues. Project context files or session logs can record work completed, rationale, open threads, errors and conventions.

Measure outcomes, not typing

Assess task completion, regressions, review burden, escaped defects, rollbacks and human intervention—not just lines generated. Context should be relevant, current and safe to retain.

Remember: persistent state prevents repeatedly reconstructing organisational context.

Which context is durable and current, and how does it affect completion and review burden?

27 / AI SOFTWARE ENGINEERING

AI-Assisted Code Review

Automate mechanical checks while keeping human review proportional to risk.

CHANGE → TESTS + REVIEW → RISK GATE → DEPLOY → OBSERVE
Explore the concept

A guarded workflow

An example sequence is AI-assisted change → local tests and lint → automated review → security checks → risk classification → human review where needed → guarded deployment → observation and rollback.

The real objective

More pull requests alone are not success. The aim is greater engineering throughput without a corresponding increase in defects or operational risk. Automated review is a supplement to—not proof of—correctness.

Watch: merged change throughput, escaped defects, review burden, revert and rollback rates, and the risk classes requiring human approval.

What happened to throughput and rollback rates, and which risk classes still need human approval?

THE CONVERSATION STARTERS

Engineering
questions.

Use these to turn an optimisation claim into an evidence-based discussion.

  1. What bottleneck are we removing, and what profiling evidence identifies it?
  2. Which metric improved, under what model, sequence lengths, concurrency and latency SLO?
  3. What changed for TTFT, TPOT, throughput and quality—not just the headline number?
  4. Is KV reuse or retrieval cheaper than recomputing the same prefix?
  5. How much communication remains on the critical path after overlap?
  6. What is the cost per useful token at the customer’s latency target?
  7. What trade-off or new bottleneck did the change introduce?

QUICK REFERENCE

Glossary.

The vocabulary behind the system.

Prefill
Processing the input prompt and producing initial attention state before generation.
Decode
Generating output tokens sequentially while using prior context.
KV cache
Stored attention keys and values for processed tokens, reused during inference.
TTFT
Time to first token: elapsed time before the first output token arrives.
TPOT
Time per output token: a measure of generation pace after the first token.
Throughput
Work completed per unit time, such as output tokens per second.
Goodput
Useful work completed per unit time while meeting the chosen service objectives; definitions vary.
SLO
Service-level objective: a measurable target for service performance.
ISL / OSL
Input sequence length / output sequence length, typically measured in tokens.
HBM
High-bandwidth memory close to the accelerator, used for active model and inference state.
DRAM / NVMe
Host memory / a storage interface, often used as larger but slower tiers than GPU memory.
RDMA
Remote direct memory access: a way to transfer data across machines with reduced CPU involvement.
Arithmetic intensity
Operations performed per byte moved, used to reason about compute and bandwidth limits.
Quantisation
Representing values with reduced precision to reduce storage or enable faster computation.
Prefix cache hit
Finding reusable state for a matching prefix; specify whether the hit rate counts requests, tokens or blocks.
Critical path
The sequence of dependent work that determines completion time; only exposed delays extend it.
